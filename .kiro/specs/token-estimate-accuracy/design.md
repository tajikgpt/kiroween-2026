# Проектирование: точность оценки входных токенов

## Где это живёт

`src/lib/billing.php`, функция `sx_estimate_input_tokens()`. Она
вызывается из двух мест, и это главное ограничение проекта:

1. **Резерв** — `src/web/gateway.php` перед `sx_reserve()`. Здесь
   завышение бьёт по клиенту: резерв больше настоящей цены.
2. **Расчёт при отсутствии `usage`** — там же, в ветке
   «провайдер не прислал usage». Здесь занижение бьёт по нам: запрос
   уходит дешевле себестоимости.

Поэтому новая формула обязана остаться **завышающей**, но умеренно.
Цель — коридор от 1.0 до 1.2, а не точное попадание.

## Рассмотренные варианты

### A. Отдельные формулы для резерва и для расчёта

Для резерва считать точно, для расчёта — с запасом.

Отклонено. Две формулы разойдутся, и расхождение проявится только в
редкой ветке «провайдер не прислал usage», где его никто не заметит.
Одна функция с предсказуемым поведением надёжнее.

### B. Настоящий токенизатор

Подключить BPE-токенизатор и считать точно.

Отклонено. На shared-хостинге нет возможности поставить расширение,
а реализация BPE на PHP для каждого запроса с 30 000 токенов — это
заметное время на каждом обращении. Платим процессором за точность,
которая нужна только для резерва.

### C. Один делитель по байтам

```php
return intdiv(strlen($text) * 10, 36) + 1;   // байт / 3.6
```

Выбрано. Байты уже учитывают разницу алфавитов: латиница — один байт на
символ, кириллица в UTF-8 — два. Делитель один, поведение понятное.

Проверка делителя на обоих алфавитах:

| текст | символов | байт | оценка | настоящих | превышение |
|---|---|---|---|---|---|
| английский | 28 696 | 28 696 | 7 971 | ≈7 174 | ×1.11 |
| русский | 1 000 | ≈1 900 | 528 | ≈450 | ×1.17 |

Оба значения в коридоре и оба завышают. Это и нужно.

## Как считается размер блоков не-текста

Сейчас каждая часть содержимого, не являющаяся текстом (изображение),
добавляет к строке 4000 символов-заполнителей. Это остаётся без
изменений: стоимость изображения у провайдеров считается иначе, и
подгонять её под ту же формулу смысла нет.

## Влияние на резерв

Резерв входа считается как `оценка + 15%` (`reserve_margin_pct`).
Для запроса Claude Code с 30 000 настоящих входных токенов на модели
`coder` (×9) и `max_tokens: 32000`:

| | сейчас | после |
|---|---|---|
| оценка входа | ≈49 000 | ≈30 600 |
| резерв входа | 507 500 | 317 000 |
| резерв выхода (25% от 32 000) | 72 000 | 72 000 |
| **резерв всего** | **579 500** | **389 000** |
| настоящая цена запроса | 265 400 | 265 400 |
| превышение резерва | ×2.18 | ×1.47 |

389 000 укладывается в приветственные 500 000 — требование 2 из
`requirements.md` выполняется.

Надбавку 15% трогать не нужно: она защищает от того, что оценка по
длине текста в принципе не знает про разбиение на токены.

## Риски

**Резерв станет меньше, значит слабее защита от параллельных запросов.**
Проверено логикой расчёта: `sx_settle()` списывает `min(факт, баланс)`,
в минус баланс не уходит, недобор пишется в журнал как наш убыток.
Худший случай ограничен и уже обрабатывается — новой дыры не появляется.

**Занижение в ветке без `usage`.** Коридор выбран так, что формула
завышает на обоих алфавитах. Если провайдер пришлёт текст на языке с
другой плотностью (например, китайский: 3 байта на символ в UTF-8,
плотность около 1 символа на токен), оценка даст `3n/3.6 = 0.83n` при
настоящих `n` — **занижение**. Это надо проверить отдельно и при
необходимости добавить нижнюю границу по числу символов.

## Проверка

1. Прогон обоих наборов тестов до изменения — зафиксировать 78 и 7.
2. Таблица «превышение» из этого документа воспроизводится скриптом на
   тех же данных.
3. Живой запрос из Claude Code на аккаунте с балансом ровно 500 000:
   должен пройти.
4. Сверка списания с `usage` в ответе вручную: `charged` обязан
   совпадать с `(вход + выход) × коэффициент`.
