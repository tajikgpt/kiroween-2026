# Два протокола, один конвейер

Шлюз отвечает на двух несовместимых протоколах:

```
OpenAI       POST /v1/chat/completions
             GET  /v1/models
Anthropic    POST /v1/messages
             POST /v1/messages/count_tokens
```

Второй нужен потому, что Claude Code говорит только на нём. Перевод
форматов — `src/lib/anthropic.php`, конвейер — `src/web/gateway.php`.

## Главное правило: биллинг один

Проверка ключа, резерв, обращение к провайдеру и расчёт — **один раз в
коде**, общие для обоих протоколов. Запрос Anthropic приводится к
внутреннему виду сразу после разбора тела, дальше работает тот же путь.

Соблазн написать отдельный `messages.php` велик, но две копии биллинга
однажды разойдутся, и разойдутся они в деньгах.

## Форма ошибки выбирается один раз

```
OpenAI:    {"error": {"message", "type", "param", "code"}}
Anthropic: {"type": "error", "error": {"type", "message"}}
```

Протокол определяется путём и запоминается в `sx_api_flavor()` **до
проверки ключа**. Дальше `sx_error()` сама отдаёт нужную форму. Мест
вызова у неё больше десятка — ветвить каждое вручную значит однажды
пропустить одно и отдать клиенту Claude Code чужой формат, который он
покажет как сбой разбора, а не как «неверный ключ».

## Сообщения об ошибках должны говорить, что исправить

Текст провайдера наружу не пересылается: в нём бывают его внутренние
адреса, настоящие имена моделей и его тарифы. Но «Сервис временно
недоступен» на каждый случай тоже не годится.

Поэтому отказ провайдера сводится к короткому коду
(`sx_upstream_reason()`), по которому шлюз подбирает своё сообщение.
Примеры настоящих причин, которые клиент исправляет сам:

- рассуждающая модель израсходовала весь `max_tokens` на рассуждение и
  не дошла до ответа — надо увеличить лимит;
- схема инструментов не прошла проверку провайдера;
- промпт длиннее контекста модели.

При нехватке баланса в ответе разбирается сумма: сколько пришлось на
вход, сколько на резерв под выход, какие коэффициенты. Без этого клиент
с балансом 100 000 видит «нужно 678 699» и не понимает, что почти всё
это — резерв, а не цена запроса.

## Коэффициенты в ответе должны быть те, по которым считают

У дорогих моделей вход и выход тарифицируются по-разному
(`coef_in_milli`, `coef_out_milli`). Поле `coefficient` в каталоге —
усреднённое число для витрины, в расчёте оно не участвует.

Выводить его рядом с ценами нельзя: клиент поделит `required_tokens` на
это число и получит величину, которой в расчёте не было. Показывать
нужно обе ставки либо восстанавливать их из цены.

## Отказ провайдера в потоке

В потоковом режиме отказ приходит кодом 4xx и телом JSON, а не потоком
SSE. Без проверки кода ответа это выглядит как успешный пустой ответ:
curl ошибки не сообщает, строк `data:` в теле нет, `usage` нет — и
шлюз считает выход по оценке и **списывает за ответ, которого не было**.

Поэтому `sx_upstream_stream()` проверяет `CURLINFO_HTTP_CODE` и при
4xx/5xx с пустым содержимым возвращает ошибку, а резерв возвращается
клиенту.

## Вызовы инструментов

Потоковый разбор обязан собирать `delta.tool_calls`, а не только
`delta.content`. Аргументы приходят по частям и склеиваются по индексу.
Если их отбросить, агент не сможет ни прочитать файл, ни записать —
весь его рабочий цикл построен на вызовах инструментов.

Пустые аргументы должны уходить как `{}`, а не `[]`. В PHP это одно
значение, и `json_encode([])` даёт массив, на котором SDK падает.
