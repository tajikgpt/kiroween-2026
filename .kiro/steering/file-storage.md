# Хранение в файлах без СУБД

Платформа работает на shared-хостинге, где MySQL недоступен. Данные
лежат в файлах. Это накладывает правила, нарушение которых уничтожает
данные — не портит, а именно уничтожает.

Реализация: `src/lib/store.php`. Доказательство необходимости:
`src/cli/test_concurrency.php`.

## Блокировка берётся ДО чтения

```php
sx_with_lock("user_{$id}", function () use ($id) {
    $u = sx_user_load($id);     // читаем ПОД блокировкой
    // ... меняем ...
    sx_user_save($u);
});
```

Схема «прочитать → изменить → записать» без блокировки на чтении
выглядит рабочей и ломается под нагрузкой. В тесте
`test_concurrency.php` она воспроизведена: 12 параллельных процессов,
и результат — **не потеря одного списания, а потеря самого
пользователя**. Процесс читает файл в момент чужой перезаписи, получает
из `json_decode()` значение `null` и записывает обратно строку `"null"`.

Поэтому: `flock` берётся до `file_get_contents`, а не между чтением и
записью.

## Один файл на сущность

```
data/
  users/{id}.json           баланс, резервы, счётчики
  keys/{sha256}.json        → user_id; имя файла и есть индекс, поиск O(1)
  ledger/{id}.jsonl         движение токенов, только дописывание
  usage/{id}-{YYYY-MM}.jsonl журнал запросов
```

Не общий `users.txt`. Блокировка получается на одного пользователя,
а не на всю базу, поэтому разные клиенты друг друга не ждут.

## Резервы внутри файла пользователя

Открытые резервы хранятся полем `resv` в том же файле, а не отдельными
файлами. Одна блокировка на всю операцию и экономия инодов — на
shared-хостинге их лимит достигается быстрее, чем место на диске.

## Данные вне веб-корня

`data/` и `.env` лежат в каталоге, который не обслуживает ни один
виртуальный хост. При файловом хранении расположение каталога — это
единственное, что отделяет балансы и хеши ключей от прямого скачивания
по ссылке. Права: `.env` 600, `data/` 700.

Дополнительно в `.htaccess` закрыты расширения `.jsonl`, `.env`, `.log`
и `.bak` — на случай, если каталог однажды окажется внутри веб-корня.

## Ключи API хранятся только хешем

В файле — `sha256` и первые символы для показа в кабинете. Полный ключ
не хранится нигде. Следствие, с которым надо смириться: потерянный ключ
нельзя восстановить, только выпустить новый. Это осознанный размен —
утёкший бэкап не отдаёт ключи клиентов.

## Чего не делать

- Не писать в `data/` из кода в веб-корне напрямую, минуя `store.php`.
- Не добавлять «временные» файлы рядом с данными: каталог просматривается
  при восстановлении баланса.
- Не менять формат строки реестра. Он только дописывается, и старые
  строки должны читаться новым кодом.
